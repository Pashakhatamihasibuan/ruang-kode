Mini 3: Isolasi data multi-tenant dengan Row-Level Security

Buka versi interaktif

Masalah. Aplikasi SaaS kasir melayani ribuan toko dalam satu database. Satu bug WHERE yang terlupa bisa membocorkan penjualan toko lain. Terapkan RLS sebagai lapisan pengaman kedua yang tetap aman walau aplikasi lupa memfilter.

Fitur wajib:
1. Kolom tenant_id di setiap tabel bisnis dan indeksnya
2. Policy USING dan WITH CHECK berbasis setelan sesi app.tenant_id
3. FORCE ROW LEVEL SECURITY dan role aplikasi tanpa hak BYPASSRLS
4. Bukti: tanpa konteks tidak melihat apa pun, tidak bisa menyisipkan data ke tenant lain

Penyelesaian langkah demi langkah:
1. Tambahkan tenant_id NOT NULL + indeks agar filter RLS tetap cepat.
2. Aktifkan dan paksa RLS, lalu buat policy dengan current_setting(..., true) agar gagal aman.
3. Aplikasi memanggil SET LOCAL app.tenant_id di awal setiap transaksi.
4. Uji tiga skenario: tanpa tenant, tenant 1 (update dan sisipan jahat), tenant 2.

Kembangkan sendiri: uji performa dengan 10.000 tenant, dan pastikan pooler PgBouncer mode transaction tetap aman karena memakai SET LOCAL.

SQL
-- SaaS kasir: banyak toko (tenant) dalam satu database, data tidak boleh bocor antar-tenant
CREATE TABLE tenant (id int PRIMARY KEY, nama text);
CREATE TABLE penjualan (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, tenant_id int NOT NULL REFERENCES tenant,
                        produk text, total numeric NOT NULL);
CREATE INDEX ON penjualan (tenant_id);
INSERT INTO tenant VALUES (1, 'Kopi Senja Medan'), (2, 'Warung Bu Tini Bandung');
INSERT INTO penjualan (tenant_id, produk, total) VALUES (1, 'Kopi susu', 25000), (1, 'Croissant', 30000), (2, 'Nasi rames', 18000);

ALTER TABLE penjualan ENABLE ROW LEVEL SECURITY;
ALTER TABLE penjualan FORCE ROW LEVEL SECURITY;             -- pemilik tabel pun tunduk pada policy
CREATE POLICY isolasi_tenant ON penjualan
  USING (tenant_id = current_setting('app.tenant_id', true)::int)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::int);

CREATE ROLE tenant_app NOLOGIN;
GRANT SELECT, INSERT, UPDATE ON penjualan TO tenant_app;
GRANT USAGE ON SEQUENCE penjualan_id_seq TO tenant_app;

SET ROLE tenant_app;
-- 1) Tanpa konteks tenant: tidak melihat apa pun (gagal aman)
SELECT count(*) AS terlihat_tanpa_tenant FROM penjualan;
-- 2) Aplikasi menyetel tenant dari token login, per transaksi
BEGIN; SET LOCAL app.tenant_id = '1';
SELECT tenant_id, produk, total FROM penjualan;
UPDATE penjualan SET total = 0;                              -- hanya baris tenant 1 yang tersentuh
INSERT INTO penjualan (tenant_id, produk, total) VALUES (2, 'Sisipan jahat', 1);
ROLLBACK;
-- 3) Tenant 2 melihat datanya sendiri dan tidak terpengaruh
BEGIN; SET LOCAL app.tenant_id = '2';
SELECT tenant_id, produk, total FROM penjualan;
COMMIT;
RESET ROLE;

Poin penting

  • Proyek mini: Isolasi data multi-tenant dengan Row-Level Security.
  • Kolom tenant_id di setiap tabel bisnis dan indeksnya
  • Kode penyelesaian lengkap ada di bawah; ketik ulang, jangan disalin.

Cek pemahaman

Kenapa memakai SET LOCAL, bukan SET, untuk app.tenant_id di balik connection pooler?

Jawaban: SET LOCAL hanya berlaku sampai transaksi selesai, sehingga koneksi yang dipakai ulang tidak membawa tenant pengguna sebelumnya

Konteks bocor antar-request adalah bug klasik pooler.
