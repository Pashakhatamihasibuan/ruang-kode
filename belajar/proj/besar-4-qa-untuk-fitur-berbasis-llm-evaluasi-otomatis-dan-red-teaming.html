Besar 4: QA untuk fitur berbasis LLM: evaluasi otomatis dan red teaming

Buka versi interaktif

Masalah. E-commerce meluncurkan asisten CS berbasis LLM yang menjawab pertanyaan retur, ongkir, dan status pesanan. Tes konvensional tidak cukup karena jawabannya tidak deterministik. Asisten pernah menjanjikan refund di luar kebijakan dan mengulang nomor HP pelanggan di jawaban.

Fitur wajib:
1. Golden set 300 pertanyaan dari tiket CS nyata (dimasking) dengan kriteria lulus per kasus
2. Metrik otomatis: fakta benar, aman, bersumber, bahasa, latensi p95
3. Quality gate di CI: setiap perubahan prompt/model/dokumen dievaluasi dan dibandingkan baseline
4. Red teaming: prompt injection, janji palsu, kebocoran PII, indirect injection
5. Pemantauan produksi: sampel jawaban direview manusia, umpan balik pengguna, insiden

Penyelesaian langkah demi langkah:
1. Kumpulkan dan masking tiket CS, lalu tulis kriteria lulus per kasus bersama tim CS.
2. Bangun runner evaluasi dengan suhu 0, aturan deterministik, dan LLM-as-judge yang dikalibrasi dengan penilaian manusia.
3. Pasang quality gate di CI untuk perubahan prompt, model, atau dokumen sumber.
4. Susun suite red team dan jalankan sebelum setiap rilis.
5. Pantau produksi, masukkan kegagalan nyata ke golden set, dan laporkan tren kualitas bulanan.

Standar industri yang dinilai: kualitas LLM diukur dengan golden set berversi, keselamatan 100% pada kasus terlarang, regresi diblok di CI, red teaming berkala, kegagalan produksi kembali menjadi kasus uji

Arsitektur dan stack (Python, pytest, Claude/LLM API, promptfoo atau Inspect/DeepEval, LLM-as-judge dengan rubrik, Langfuse/OpenTelemetry, GitHub Actions)
BagianIsi
Data ujigolden set berlapis kategori (retur, ongkir, pembayaran, keluhan), versi dikelola di Git
Penilaianaturan deterministik dulu (harus memuat/dilarang), lalu LLM-as-judge berubrik untuk kualitas
Gerbangaman = 100%, fakta ≥ 90%, tidak boleh turun > 2 poin dari baseline
Adversarial120 kasus red team diperbarui setiap bulan dari temuan produksi
Produksi1% percakapan direview manusia, label "AI", jalur eskalasi ke agen manusia
Metriktingkat jawaban benar, insiden kebijakan, eskalasi, CSAT, biaya per percakapan

  • Stack: Python, pytest, Claude/LLM API, promptfoo atau Inspect/DeepEval, LLM-as-judge dengan rubrik, Langfuse/OpenTelemetry, GitHub Actions.

Cek pemahaman

Kenapa aturan deterministik (harus memuat/dilarang) dijalankan sebelum LLM-as-judge?

Jawaban: Lebih murah, cepat, dan pasti untuk fakta kunci dan larangan; judge dipakai untuk aspek kualitas yang sulit diaturkan

Gabungkan cek pasti dan penilaian berubrik.
