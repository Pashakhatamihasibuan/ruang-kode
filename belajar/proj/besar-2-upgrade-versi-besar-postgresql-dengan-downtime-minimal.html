Besar 2: Upgrade versi besar PostgreSQL dengan downtime minimal

Buka versi interaktif

Masalah. Perusahaan logistik masih memakai PostgreSQL 12 yang sudah end-of-life, dengan database 2 TB yang melayani pelacakan paket 24 jam. pg_upgrade di tempat berisiko dan butuh jendela panjang. Targetnya: pindah ke PostgreSQL 16 dengan downtime di bawah 5 menit dan rencana rollback.

Fitur wajib:
1. Inventaris: ekstensi, tabel tanpa primary key, fitur usang, kompatibilitas aplikasi
2. Logical replication dari 12 ke 16 dengan salinan awal dan perubahan berjalan
3. Validasi data: jumlah baris dan checksum per tabel
4. Sinkronisasi sequence dan cutover lewat PgBouncer PAUSE/RESUME
5. Rollback plan: server lama dipertahankan dan bisa menjadi tujuan replikasi balik

Penyelesaian langkah demi langkah:
1. Audit kompatibilitas dan perbaiki tabel tanpa primary key.
2. Bangun server 16, salin skema, buat subscription, dan pantau sampai lag nol.
3. Jalankan validasi data otomatis dan uji beban baca di server baru.
4. Gladi bersih cutover di staging dengan stopwatch; susun runbook menit per menit.
5. Cutover produksi di jam sepi, pantau, dan pensiunkan server lama setelah masa aman.

Standar industri yang dinilai: downtime terukur sesuai target, data tervalidasi dengan checksum, sequence tersinkron, runbook dan rollback teruji di gladi bersih

Arsitektur dan stack (PostgreSQL 12 → 16, logical replication (publication/subscription), pg_dump --schema-only, PgBouncer, pgBackRest, skrip validasi Python)
BagianIsi
Persiapanwal_level = logical, replica identity semua tabel, uji aplikasi di 16 (staging)

SQL
-- Upgrade PostgreSQL 12 (EOL) -> 16 dengan logical replication: downtime hanya beberapa detik saat cutover
-- ===== Di server LAMA (12) =====
ALTER SYSTEM SET wal_level = logical;                     -- butuh restart terjadwal sekali
CREATE ROLE replikator WITH LOGIN REPLICATION PASSWORD :'sandi';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO replikator;
-- Semua tabel wajib punya primary key atau REPLICA IDENTITY agar UPDATE/DELETE bisa direplikasi
SELECT c.relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r'
  AND NOT EXISTS (SELECT 1 FROM pg_index i WHERE i.indrelid = c.oid AND i.indisprimary);
CREATE PUBLICATION pub_upgrade FOR ALL TABLES;

-- ===== Di server BARU (16) =====
-- 1) Skema saja: pg_dump --schema-only -d toko_lama | psql -d toko
-- 2) Langganan: salinan awal + perubahan berjalan
CREATE SUBSCRIPTION sub_upgrade
  CONNECTION 'host=db-lama.internal dbname=toko user=replikator sslmode=require'
  PUBLICATION pub_upgrade WITH (copy_data = true, streaming = on);

-- 3) Pantau sampai lag ~0
SELECT subname, received_lsn, latest_end_lsn, last_msg_receipt_time FROM pg_stat_subscription;

-- 4) Validasi data: jumlah baris dan checksum per tabel di kedua sisi
SELECT 'pesanan' AS tabel, count(*), md5(string_agg(id::text || total::text, ',' ORDER BY id)) FROM pesanan;

-- ===== Cutover (jendela 5 menit, diumumkan) =====
-- a) Aplikasi mode baca-saja / PgBouncer PAUSE
-- b) Pastikan lag 0, lalu SINKRONKAN SEQUENCE (logical replication tidak membawa nilai sequence):
SELECT format('SELECT setval(%L, %s, true);', sequencename, last_value)
FROM pg_sequences WHERE last_value IS NOT NULL;           -- jalankan di lama, eksekusi hasilnya di baru
-- c) DROP SUBSCRIPTION sub_upgrade;  arahkan PgBouncer ke server baru;  RESUME
-- d) ANALYZE semua tabel di server baru; pantau pg_stat_statements 24 jam; server lama dibiarkan 7 hari untuk rollback

Cek pemahaman

Kenapa nilai sequence harus disinkronkan manual saat cutover dengan logical replication?

Jawaban: Logical replication menyalin baris tabel tetapi tidak menyalin posisi sequence, sehingga INSERT pertama di server baru bisa bentrok primary key
