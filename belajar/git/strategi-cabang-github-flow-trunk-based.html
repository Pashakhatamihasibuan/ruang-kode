Strategi cabang: GitHub Flow & trunk-based

Buka versi interaktif

Tim perlu kesepakatan cara memakai cabang. GitHub Flow paling sederhana: main selalu siap rilis; setiap pekerjaan dibuat di cabang pendek, dibuka pull request, ditinjau, lalu digabung dan dirilis.

Trunk-based development lebih ekstrem: cabang hidup paling lama sehari atau dua hari, dan fitur yang belum selesai disembunyikan dengan feature flag. Cocok untuk tim yang rilis berkali-kali sehari dengan tes otomatis yang kuat.

Git Flow memakai cabang develop, release/*, dan hotfix/*. Masih dipakai untuk produk dengan jadwal rilis berversi (misalnya aplikasi desktop), tetapi terlalu berat untuk kebanyakan aplikasi web. Apa pun pilihannya, beri nama cabang yang jelas.

TERMINAL
# GitHub Flow sehari-hari
git switch main
git pull
git switch -c fitur/filter-harga      # nama cabang: jenis/ringkasan
# ... ubah kode, commit kecil-kecil ...
git push -u origin fitur/filter-harga
gh pr create --fill                   # buka pull request
# setelah disetujui dan digabung:
git switch main && git pull
git branch -d fitur/filter-harga

Poin penting

  • GitHub Flow: main selalu siap rilis, cabang pendek + PR.
  • Trunk-based: cabang 1-2 hari + feature flag.
  • Git Flow: untuk rilis berversi, lebih berat.
  • Nama cabang: jenis/ringkasan.

Cek pemahaman

Ciri utama trunk-based development?

Jawaban: Cabang sangat pendek dan fitur belum jadi disembunyikan dengan feature flag

Integrasi sering mengurangi konflik besar.

Jawaban: Selalu siap dirilis
